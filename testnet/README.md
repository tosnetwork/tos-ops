# Public testnet

Settings, scripts and units for the TOS public testnet: a multi-host network
run by independent operators, between the single-host local network
(`local/`) and production (`production/`).

Start with [OPERATOR.md](OPERATOR.md) for independent validator operations,
[CEREMONY.md](CEREMONY.md) for the coordinator and genesis sequence, and
[AGENTS.md](../AGENTS.md) for approval and secret-handling rules. Production
choices are proposals in [Production-Node.md](../production/Production-Node.md),
not a replacement for this testnet's profile and installers.

Documentation checked against tos-ops main `8e64906` and tos
`85c679c3454f306eb867e25b1960ae3d757bd3dd`. This is a reusable runbook, not a
live status report. `profile.json` has an epoch-4 AUTH tag but its prose status
still says epoch 3; use the approved ceremony artifacts and live checks for
network identity and current state. Do not infer live state from that note.

## What differs from production and from local

| | Local (`local/`) | Public testnet (here) | Production |
| --- | --- | --- | --- |
| Global id (ConfigParam 19) | 3 | **2**, confirmed 2026-10-12 (decision D03) | 1 |
| Genesis | test harness, keys made by the installer | operator ceremony, `validator-pq.pub` | operator ceremony |
| Genesis template | harness template | pinned `gen-zerostate.fif`, with reviewed global id, epoch, schedule and AUTH tag | canonical template |
| Hosts | one | one validator per host, separate DHT hosts | same |
| Keys | deterministic or generated by the installer | consensus seed generated on each validator host; operator wallet in the host's vault; pool owner key on the coordinator | same |
| Election timings | 600 s development profile | 14,400 s terms; 21,600 s initial set | canonical template, per release |
| Engine options | `--quic-flood-control -1`, short TTLs | production options | production options |
| Shielded pool, Energy | development pool deployed | Energy **disabled**; shielded pool **restricted epoch-6 test** only (`features.shielded_pool_record`), otherwise disabled until its gate passes | per release |

Nothing from `local/` is used here: no deterministic seeds, no faucet wallet,
no `local-pq-*` drivers, no development pool key.

The scripts need only Python 3.10+ and the release binaries on a node host.
The coordinator also needs a tos checkout and build (`TOS_ROOT`, `--tos-build`,
and its `fift` for the pool owners). If operators cannot access this private repository, hand them `testnet/` as a bundle (it holds no secrets) or
publish it with the operator documentation. On a host, place it in a
root-owned, world-readable directory such as `/opt/tos-testnet`; the service
account runs some of the scripts.

No testnet service runs as root. The nodes run as `tos`; the election task
(`tosctl service`) as `tos-ctl`, a non-login system user that owns only
`/var/lib/tos-ctl` (`init-operator.sh` creates it, and runs every `tosctl`
call as it: tosctl refuses a vault, lock or key file its caller does not own);
the alert peer as `tos-alert`, which owns only `/var/lib/tos-alert`. The
secrets those two read stay root-owned, mode 0600: systemd reads
`/etc/tos/tosctl.env` (the vault master key) before it drops privileges, and
hands `/etc/tos-alert/{token,chat}` to the peer with `LoadCredential=`. To run
`tosctl` by hand on a validator host:

```bash
sudo bash -c 'set -a; . /etc/tos/tosctl.env; set +a; cd /var/lib/tos-ctl; runuser -u tos-ctl -- tosctl wallet ls'
```

A host set up while these ran as root moves over once with
`migrate-nonroot-services.sh --role validator` (or `--role dht`), after the
updated `testnet/` is installed: it stops the unit only for the ownership
change, a vault check and the restart, verifies the new unit runs as the new
user, and on any failure puts back the old unit and every owner and mode and
starts it again. It cannot see the chain: run the validator role outside an
open election.

| Observer | at least 2 independent (G0, planned) | a full node another party runs | as full node |

The tooling does not establish which hosts are currently deployed. Verify the
approved private inventory. The read-only [network checker](../production/scripts/README.md)
provides held-anchor proof and Elector-result checks over HTTP; its
[recorded evidence](../production/evidence/README.md) states the remaining
historical-proof availability limit. The supplied alert peer has no independent
chain view.

Validators serve no public clients. A validator's JSON-RPC (8081) and exporter (9100)
stay on loopback; its console (30002/tcp) listens on every address, as the engine binds
control ports by number, so the host firewall keeps it closed and it needs its client
key. Reach all three over SSH.
QUIC always uses the ADNL port plus 1000; open both.

The validator preflight floors are 4 CPUs, 11 GiB MemTotal and 60 GiB free;
use NVMe with adequate endurance and a static IPv4. These are minimum admission
checks, not a capacity guarantee. The proposed production profile is separate. Virtual machines are fine. The public testnet's
capacity and timing numbers are not release evidence (decision D13); reports
label them `NON-RELEASE` and record the virtualization. Measured on the local
network, one validator writes about 190 GB a day to disk, so choose NVMe by
endurance, not only size.

## Genesis template patch

The canonical `gen-zerostate.fif` pins mainnet: `1 setglobalid` and a
`SOURCE_DATE_EPOCH` check for 1789434000 (its initial set is 21,600 s since
tos #206, 131,072 s before). `testnet-coordinator.py genesis` copies the template
into the ceremony directory and replaces exactly those three lines, plus the
five named constants that set the validator schedule (`orig_vset_valid_for`,
`validators_elected_for`, `elections_start_before`, `elections_end_before`,
`stakes_frozen_for`, from the profile); if any of them is missing or appears
twice, the template changed and the ceremony refuses. The template checks its
first election against those constants before writing any state (since tos
#324), so each constant must be bound once, above that schedule guard, and
`config.election_params!` must be written from the names after it; a template
in any other shape, including the one before tos #324, is refused. It also inserts one line
after the first, `0x<tag> constant quantum-network-tag`, the AUTH network tag
the template's own guard demands for version 16, and refuses a template whose
guard is gone or that already defines a tag or the admission candidate. The patched copy, the original's SHA-256, the tos revision and the
`create-state` digest are recorded in `genesis.json`, and genesis is generated
twice in separate directories and must be byte-identical. tos itself is not
modified.

## Watching the network

At the pinned tos revision, retired consensus databases become eligible only
once the durable GC floor proves them obsolete; cleanup is enabled by default.
A key block permits GC progress but does not guarantee an immediate deletion.
Historical epoch-3 observations: about 10 MB a
minute idle, 31 MB a minute at ~6.4M gas per block, back to about 750 MB after
each election. These are observations, not disk bounds. One host, on the host:

```bash
sudo python3 /opt/tos-testnet/scripts/check-host-disk.py --min-free-gib 15 --cpu-sample 3
```

It prints free space, `consensus/` size and session count, the validator
unit's state, restarts and memory, the head seqno and age, the block-download
net failures and refused answers, and CPU busy and iowait; it exits 1 below
the floor. A value it could not observe is null, not 0.

All validators, from the coordinator (the hosts need nothing installed; the
probe is piped over SSH):

```bash
testnet/scripts/watch-testnet.py --inventory hosts.json --out epoch/series.tsv \
    --interval 60 --duration 1800
```

It appends one TSV row per host per round and prints `ANOMALY` / `RECOVERED`
lines when the set of anomalies changes (unreachable, unit not active, restart
count changed, head older than 120 s, head unchanged for three rounds, a burst
of five or more net failures in one round, free space below 20 GiB) and a
`SUMMARY` of heights every 15 minutes. Typical uses:

- the epoch watch: `--interval 60`, re-armed for as long as the epoch runs;
- the `consensus/` and memory series: `--interval 900`;
- a load test: `--interval 60 --cpu-sample 3` for the load window;
- a restarted validator's catch-up (CON-06): start it right after the
  restart with `--hosts node-4 --interval 30 --until-current node-4
  --duration 2400`; it prints `CURRENT ... after N s` once the shard client
  age falls below 60 s, or `NOT CURRENT` and exits 1.

After each rotation, confirm the elected set with the same records file used
at genesis:

```bash
TOS_ROOT=$TOS_ROOT "$TOS_ROOT/.venv/bin/python" testnet/scripts/check-testnet.py \
    --genesis genesis.json --rpc URL --rpc URL --elected-set genesis-records.json
```

It requires as many members as records, all main validators, with exactly the
records' validator ids, the staking pools (consensus keys may change at an
election), and prints
the set's `utime_since`/`utime_until`. This operator-record check does not prove
the Elector's result. For Config34's active election and Config32's historical
active election, use the [HTTP checker](../production/scripts/README.md) with the
approved global config, AUTH pin and [independently built verifier](../production/scripts/README.md#build-the-verifier).

### Checking a validator-set handover

`check-handover.py` checks that every masterchain block on both sides of a
handover is finalized by the set the chain selected for it. Collect around the
incoming set's `utime_since` (`--boundary`, or its alias `--term-start`), with
one JSON-RPC URL per validator, from the coordinator:

```bash
testnet/scripts/check-handover.py collect --boundary UNIXTIME \
    --rpc URL1 --rpc URL2 --rpc URL3 --rpc URL4 \
    --genesis-config global.config.json --span 100 --out epoch/handover-DATE
TOS_ROOT=$TOS_ROOT "$TOS_ROOT/.venv/bin/python" testnet/scripts/check-handover.py verify \
    --genesis-config global.config.json --out epoch/handover-DATE
```

`collect` is read-only (an allow-list of read methods), starts requests to one
node at least 0.6 s apart (`--interval`; `--lock-dir` shares the spacing with
other processes) and appends every request with the hash of its answer to
`journal.jsonl`. It may be started before the boundary: it waits for the
boundary and for every head to pass the range, up to `--max-wait` seconds. For
the `--span` blocks on each side of the block at the boundary time it records
each node's certificate, lookup, header and shard tops, ConfigParam 34 at every
set-source key block, and ConfigParam 32/34 at the range end, in
`collection.json`. When a node has already garbage-collected a source key
block's state, ConfigParam 34 is read at the first collected non-key block whose
agreed header names that source, and the substitution is recorded.

`verify` is offline. It decodes each set itself, binds every block's set
through its header (`prev_key_block_seqno` selects the key block whose
ConfigParam 34 applies) and verifies every node's certificate against that set:
every ML-DSA-44 signature, unique signers, two-thirds of the weight. It requires
the global config's zero state, the profile's global id, the same full ids,
header fields, shard tops and set bytes on every node, ConfigParam 32/34 after
the handover equal to the outgoing and incoming sets, contiguous roles with the
last outgoing block as the installing key block, and that the wrong-set,
spliced-signature and tampered-certificate controls are rejected. It writes
`report.json` and exits 0 only on PASS.

A block generated after its set's `utime_until` is valid while no incoming set
is installed: the chain extends the term, as after a postponed election. The
report lists such blocks under `extended_term` with their range and seconds
past `utime_until`; each must still pass the binding checks above. A block
generated before its set's `utime_since` fails.

`verify` needs the `dilithium-py` package (pure Python, tested with 1.1.0); the
tos build has no standalone ML-DSA-44 verifier, and `verify` refuses without it.
The tests replay recorded epoch-5 captures; those that run the real verifier are
skipped when the package is missing. Node agreement is detection, not a proof
chain from an authenticated anchor.

## Alerts

### Install and verify the relay

**Prerequisites:** human-approved deployment, a reviewed private inventory, SSH
BatchMode access to the peer, Telegram bot/chat provisioned by the human without
passing secrets through an agent, and an agreed acknowledgement procedure.
The peer is a heartbeat watchdog, not an independent chain observer.

1. On the coordinator, prepare the user-unit template from
   [systemd/tos-testnet-alert-coordinator.service](systemd/tos-testnet-alert-coordinator.service).
   It expects the `%h/tos-ops` checkout and inventory at
   `%h/.config/tos-alert/hosts.json`, with peer label `node-dht`. Confirm those
   inputs or obtain a reviewed template change before installing; do not edit an
   installed unit. Provision coordinator token/chat files privately at mode 0600.
2. On the peer, root provisions `/etc/tos-alert/token` and `chat` (root-owned
   0600). Confirm the `tos-alert` non-login account exists; a new host needs it
   created before installing the unit. The unit uses systemd credentials and
   `StateDirectory=tos-alert`, not a root-run relay. With approval, install the
   reviewed bundle's template:

   ```bash
   sudo install -m 0644 /opt/tos-testnet/systemd/tos-testnet-alert-peer.service /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemd-analyze verify /etc/systemd/system/tos-testnet-alert-peer.service
   sudo systemctl enable --now tos-testnet-alert-peer
   systemctl is-active tos-testnet-alert-peer
   ```

3. On the coordinator, after the reviewed template is in the user-unit directory:

   ```bash
   systemctl --user daemon-reload
   systemctl --user enable --now tos-testnet-alert-coordinator
   systemctl --user is-active tos-testnet-alert-coordinator
   journalctl --user -u tos-testnet-alert-coordinator -n 30 --no-pager
   ```

   Arrange lingering with the human administrator if the user service must outlive
   logout. Expected: watch samples and fresh peer/coordinator heartbeat files,
   alert receipts and chat acknowledgements, not repeated credential/SSH errors.
   On failure preserve sanitized logs, verify credential modes and SSH access,
   and ask; never print tokens or disable their checks. A controlled alert and
   dead-man drill requires a separately approved window.

### Runtime behavior and silence

`scripts/alert-relay.py` turns the watch into messages to a person over a
Telegram bot. Two roles, on two hosts, each watching the other's heartbeat:

- `coordinator` (on the coordinator, `systemd/tos-testnet-alert-coordinator.service`
  as a user unit) runs `watch-testnet.py` with no duration and restarts it if
  it exits. It sends a message when an anomaly key (`node-1:head_age`,
  `node-3:unit`: host and kind, without the value) first appears, with the
  full `ANOMALY` line; one reminder per key every 30 minutes while it
  persists; and a recovery message naming what cleared. `SUMMARY` lines are
  not sent (`--digest-hours N` sends one every N hours). Every minute it
  touches `/var/lib/tos-alert/heartbeat-coordinator` on the `--peer` host over
  SSH (as root, handing the file to the directory's owner) and reads the age
  of `heartbeat-peer` there. When it starts within 15 minutes of the host's
  boot it sends one `coordinator rebooted` notice: an outage shorter than the
  dead-man window plus one peer interval (about 3.5 minutes) can fall between
  the peer's samples, yet a reboot still ends every job the coordinator was
  running or waiting to run.
- `peer` (on the DHT host, `systemd/tos-testnet-alert-peer.service`, user `tos-alert`)
  touches `heartbeat-peer` every minute and alerts when the coordinator's beat
  is older than 150 s, then reports its return. While that beat is dead it
  also reads the chat's replies (see below).

Either side alerts once when the other's beat is stale or unreadable for
`--dead-after` (150 s) and sends a recovery when it is fresh. 150 s is two
missed one-minute beats plus slack: a stopped side is reported within
dead-after + one check interval + the send (at most about 260 s), inside the
5-minute alert budget. Telegram connections try IPv4 before IPv6, 3 s per
address, so a host whose IPv6 route hangs still sends in about a second. The bot token
and chat id are files given by `--token-file` and `--chat-file`, mode 0600
(the relay refuses anything group- or world-readable): `/etc/tos-alert/` on
the DHT host, root-owned and passed to the peer as systemd credentials (the
relay accepts a credential's ACL group bits, nothing else), and
`~/.config/tos-alert/` on the coordinator. They never enter this repository.

A reply in the chat is an acknowledgement: the coordinator reads replies
every 30 s, records each in `acks.jsonl` with its time and the alert it
follows, and confirms it. While the coordinator's heartbeat is dead, the peer
reads them instead (its own offset file, its own `acks.jsonl`, each reply
recorded against the peer's last alert) and stops when the beat is fresh
again, so only one host reads at a time. getUpdates confirms what it returns
on Telegram's side, so a reply one host read is never seen by the other: the
acknowledgement receipts are split between the two hosts' `acks.jsonl`, and
reading both is the full record.

Planned work: silence each host whose alerts it would trigger before you
start, for example on the coordinator and, over SSH, on the DHT host:

```bash
testnet/scripts/alert-relay.py silence --state-dir ~/.local/state/tos-alert \
    --until +90 --reason "restart node-2 for the new build"
ssh root@DHT-HOST python3 /opt/tos-testnet/scripts/alert-relay.py silence \
    --until 2027-01-15T10:00 --reason "coordinator reboot"
```

For a planned outage of only one node, keep other failures visible:

```bash
testnet/scripts/alert-relay.py silence --state-dir ~/.local/state/tos-alert \
    --host node-4 --until +90 --reason "planned node-4 outage"
```

Repeat `--host` or use repeatable `--key node-4:unit` for exact alert keys.
Every scope requires an expiry. `unsilence --host node-4` ends that scope
without changing other scopes or the global silence. Scoped entries live in
`silence.scopes.json` beside the global file, with mode 0600. Invalid entries
silence nothing. Mixed messages send only the unsilenced keys; recoveries use
the same filtering. The next relay tick reports each ended scope and its
suppressed alerts. The peer still reads only its own local files.

Run as root, `silence` hands the file to the owner of the state directory, so
the peer (user `tos-alert`) can read it.

While silenced, alerts are recorded but not sent; when the silence expires or
`unsilence` removes it, one message lists what was suppressed and what is
still active.

Receipts: every alert, sent or silenced, is a line in `alerts.jsonl` in the
state directory (`~/.local/state/tos-alert` on the coordinator,
`/var/lib/tos-alert` on the DHT host) with its UTC time, kind, keys, text,
Telegram message id and send latency; replies are in `acks.jsonl`. A message
that cannot be sent is retried every cycle and recorded only once it goes
out, so its latency shows the delay.

Known gap: the peer has no chain access (the validators' JSON-RPC answers on
loopback only), so it watches only the coordinator's heartbeat. It can say the
coordinator's watch stopped, but while the coordinator is down nobody watches
the chain, and the chain is only ever seen through the coordinator's SSH
probes. An independent chain observer needs a public read-only endpoint, which
is not deployed.

## Verification

`scripts/rehearse-loopback.sh` runs every script above on one host with four
operators and two DHT nodes, then starts the four validators and requires
`check-testnet.py` to see one zero state, one full block id at height 20 or
more, the testnet global id and ConfigParam 34 equal to the four genesis
identities:

```bash
TOS_ROOT=$TOS_ROOT TOS_BUILD=$TOS_ROOT/build testnet/scripts/rehearse-loopback.sh /path/to/new/workdir
```

Unit tests need only pytest (the tos environment has it). With `TOS_ROOT`
set they also check the patch against the real template, and with `TOS_BIN`
naming release binaries they exercise the console set-up:

```bash
TOS_ROOT=$TOS_ROOT "$TOS_ROOT/.venv/bin/python" -m pytest -q testnet/tests
```

Each guard was broken once on purpose and the tests failed every time:
identity uniqueness, template line count, key id match, block agreement,
global id, staleness, the config lock, the confirmed-global-id gate, key
reuse across resets (validator identities and wallet keys), and the validator
schedule checks. The handover checker's checks are mutants `CH1`-`CH29` in
`tests/mutants.py` (`python testnet/tests/mutants.py CH1 CH2 ...`).

After a reset, every coordinator step that creates or onboards a wallet takes
`--previous-ceremony DIR` once per earlier epoch (`testnet-coordinator.py
genesis`, `testnet-elections.py pool`, `onboard` and `load`), beside `manifest
--previous`; see CEREMONY.md section 9.

## Deployment limits

- Independent-operator rehearsals and infrastructure-diverse observations need
  their own evidence; a single coordinator's loopback run does not establish them.
- The pool and onboarding code has local tests. Live acceptance and current
  network state belong to the approved ceremony record, not this README. Verify
  the node's custody line, the pool's roles and the service state after every
  change.
- No public RPC deployment, explorer or faucet service is provided by this
  directory. Templates and funding tools do not deploy those services automatically.
- Journal gates recognize only fully matched election-task pool messages; unrelated
  or unverifiable activity remains unexplained and blocks the gate.
- Preflight admits aarch64, but the supplied host build script sets x86-64-v2;
  follow this runbook on Ubuntu 24.04 x86_64 only unless a separate build is reviewed.
- The alert peer sees the coordinator heartbeat, not chain state. Independent
  chain observation requires another approved endpoint/deployment.

### Qualified load evidence

`testnet-elections.py load --qualify-load` adds bounded, durable evidence to the
existing load driver. Supply distinct `--rpc` and `--confirm-rpc`, the approved
`--expected-genesis-root` and `--expected-genesis-file` (64 lowercase hex digits
each), a positive `--funding-ceiling` and a positive `--fee-stop`, in TOS. All
watched RPC sources must report that full genesis before keys/deployment and at
periodic safety checks. This is RPC corroboration; the execution packet still
needs its separate native genesis/configuration/source-funds proofs.

The funding ceiling bounds the sum of new owner transfer amounts in **one run**,
including initial deployment and refills. It does not include the owner's own
transfer fees or previously funded assets. The fee-stop is an observed net-burn
stop for load wallets, sampled at safety checks; it excludes deployment/owner
fees, can be affected by other inflows, and does not bound costs still in flight.
It is not an exact total-fee guarantee. Preserve the source owner's reserve and
set a separately reviewed total allocation for all trials and retained balances.

Every offered query gets private retained original carrier bytes and a durable
public-metadata event. Execution is checked for **each query** on both RPC
sources; the old last-query group proxy is not used in qualified mode. Latency is
from RPC offer to wallet-sequence acceptance / observed processed status, not
key generation, signing, native finality or full application latency.
The first execution check is eligible immediately after sequence acceptance;
qualified observations do not add the ordinary mode's three-second hold. Polling
and RPC time still contribute to the observed latency; it is not chain finality.
Histograms have fixed buckets, the seen-ID bitmap is 1 MiB and the live table is capped at
8,192 queries. Retained carrier/disk growth is expected workload evidence, not
in-memory retention. Never publish or hash private outbox carriers or keys.

A send/funding uncertainty stops new work. The private unfinished-run marker
refuses a new qualified run until the original result is reconciled; there is no
automatic retry, re-sign or resume flag. Successful normal completion releases
the process lock and closes the run marker only when no queries or unknown
funding remain. The lock file is retained. These observations alone do not prove
72 hours, node resource bounds, native settlement, three trials or capacity SLOs.

Do not use `--dry-run` as an unsigned check: existing load dry-run creates keys
and signs a batch. Qualified dry-run is refused. Build an unsigned execution
packet and review the actual monitor, load profile and budgets before sending.

All load modes share the same process lock. A state with qualification history
cannot be reopened in ordinary/dry-run mode, even after a completed run; keep
using qualification mode. Qualified identities are durably bound to the full
genesis, and unbound legacy keys cannot be silently adopted. Query-counter data
and its directory are synced before signing. All send endpoints participate in
the pre-key/periodic genesis checks, and each actual send route is checked again
before its carrier is admitted.

Stopping closes admission to new carriers and funding reservations immediately;
already-started operations still need their original result reconciled. A funding
thread that outlives the bounded join leaves the run unfinished and fails the
command. A run cannot publish a safe closed marker with funding still in flight.
The offering window uses monotonic time; event monotonic timestamps also allow
gap analysis. Setup/drain time and thermal pauses do not become evidence of
sustained qualifying throughput by virtue of elapsed wall time alone.

Exceptional cleanup halts admission before waiting for worker shutdown. Qualified
carriers are capped at 1 MiB, archived once, and that exact immutable snapshot is
sent; replacing the original pathname cannot change the transmitted bytes. A
qualified CLI run returns failure unless its declared monotonic offering window
completed, every offered query was observed executed, all funding was settled,
and failed/refused/unconfirmed counts are zero. The retained summary still
exposes the narrower RPC-observation and net-burn scopes above.

The relayer refill trigger is one third of `--relayer-amount`. It must exceed
`--relayer-floor`: for example, a 10 TOS target with a 2 TOS stop floor is
accepted, while a 3 TOS target with that floor is refused before key creation or
signing. This ordering check is necessary, not a funding-latency guarantee;
leave headroom for the five-second refill check and transfer settlement.
