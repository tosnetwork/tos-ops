# Public testnet

Settings, scripts and units for the TOS public testnet: a multi-host network
run by independent operators, between the single-host local network
(`local/`) and production (`production/`).

It follows two documents and does not restate them:

- the qualification plan in the memo repository, `public-testnet/README.md`
  (phases P0–P4, gates G0–G4, decisions D01–D10). This directory is its
  deployment tooling (decision D02);
- [`../production/Production-Node.md`](../production/Production-Node.md) for
  node roles, key custody, the two-phase first start, retention and forbidden
  options. A testnet node is a production node on a different chain.

**Status: epoch 1 ran on five hosts on 2026-10-12 for 5.2 hours and was
stopped for a reset.** What it found, and what epoch 2 waits on, is memo
`public-testnet/EPOCH-1-FINDINGS.md`. The ceremony scripts also run end to end
on one host by `scripts/rehearse-loopback.sh` (see "Verification").

## What differs from production and from local

| | Local (`local/`) | Public testnet (here) | Production |
| --- | --- | --- | --- |
| Global id (ConfigParam 19) | 3 | **2**, confirmed 2026-10-12 (decision D03) | 1 |
| Genesis | test harness, keys made by the installer | operator ceremony, `validator-pq.pub` | operator ceremony |
| Genesis template | harness template | canonical `gen-zerostate.fif` with only global id and epoch replaced | canonical template |
| Hosts | one | one validator per host, separate DHT hosts | same |
| Keys | deterministic or generated by the installer | consensus seed generated on each validator host; root key offline | same |
| Election timings | 600 s development profile | canonical 65,536 s profile | canonical |
| Engine options | `--quic-flood-control -1`, short TTLs | production options | production options |
| Shielded pool, Energy | development pool deployed | **disabled** until their own gates pass | per release |

Nothing from `local/` is used here: no deterministic seeds, no faucet wallet,
no `local-pq-*` drivers, no development pool key.

The scripts need only Python 3.10+ and the release binaries on a node host.
The coordinator and anyone deriving a controller id also need a tos checkout
and build (`TOS_ROOT`, `--tos-build`). External operators cannot read this
private repository: hand them `testnet/` as a bundle (it holds no secrets) or
publish it with the operator documentation. On a host, place it in a
root-owned, world-readable directory such as `/opt/tos-testnet`; the service
account runs some of the scripts.

No testnet service runs as root. The nodes run as `tos`; the election task
(`tosctl service`) as `tos-ctl`, a non-login system user that owns only
`/var/lib/tos-ctl` (`init-operator.sh` creates it, and runs every `tosctl`
call as it: tosctl refuses a vault, lock or key file its caller does not own);
the alert peer as `tos-alert`, which owns only `/var/lib/tos-alert`. The
secrets those two read stay root-owned, mode 0600: systemd reads
`/etc/tos/tosctl.env` (the vault master key) before it drops privileges, and
hands `/etc/tos-alert/{token,chat}` to the peer with `LoadCredential=`. To run
`tosctl` by hand on a validator host:

```bash
sudo bash -c 'set -a; . /etc/tos/tosctl.env; set +a; cd /var/lib/tos-ctl; runuser -u tos-ctl -- tosctl wallet ls'
```

A host set up while these ran as root moves over once with
`migrate-nonroot-services.sh --role validator` (or `--role dht`), after the
updated `testnet/` is installed: it stops the unit only for the ownership
change, a vault check and the restart, verifies the new unit runs as the new
user, and on any failure puts back the old unit and every owner and mode and
starts it again. It cannot see the chain: run the validator role outside an
open election.

## Roles and hosts

| Role | Count at launch | Runs | Public inbound |
| --- | --- | --- | --- |
| Genesis validator | 4, one per operator, one per host | `tos-testnet-validator` | ADNL 30001/udp, QUIC 31001/udp |
| DHT bootstrap | at least 2, on separate hosts | `tos-testnet-dht` | 30300/udp |
| Full node / RPC | at least 2, team-run (planned) | `tos-testnet-fullnode` | ADNL, QUIC, lite server 30003/tcp; JSON-RPC only through a proxy |
| Observer | at least 2 independent (G0, planned) | a full node another party runs | as full node |

Epoch 3 runs the four validators and two DHT bootstraps (the DHT host and
node-1) only: the owner decided on 2026-10-15 to run no full node for now, so
there is no public RPC endpoint and no independent observer yet.

Validators serve no public clients. A validator's console (30002/tcp) and its
JSON-RPC (8081) and exporter (9100) stay on loopback; reach them over SSH.
QUIC always uses the ADNL port plus 1000; open both.

The starting hardware is the plan's section 5.3 profile: 8 vCPU, 16 GiB RAM,
200 GiB NVMe, 1 Gbit/s. Virtual machines are fine. The public testnet's
capacity and timing numbers are not release evidence (decision D13); reports
label them `NON-RELEASE` and record the virtualization. Measured on the local
network, one validator writes about 190 GB a day to disk, so choose NVMe by
endurance, not only size.

## Decisions this directory needs before the ceremony

These come from the memo plan's decision register. Where one is still open, the
scripts refuse or flag it rather than choose silently.

| Decision | Where it is used | Current value |
| --- | --- | --- |
| D03 global id | `network/profile.json` `global_id` | 2, `CONFIRMED` 2026-10-12 (mainnet 1). The scripts refuse 1 and 3, and `genesis` refuses any global id not marked `CONFIRMED` |
| D03 genesis epoch | `testnet-coordinator.py genesis --epoch` | chosen at the ceremony; refused if older than one hour or more than 14 days ahead |
| D03 validator schedule | `network/profile.json` `genesis.initial_set_valid_for_seconds` and `genesis.election_params`; `genesis` replaces the two template lines and records them in `genesis.json` | decided 2026-10-12 after the first epoch: initial set 21,600 s, ConfigParam 15 = 14,400 / 7,200 / 1,800 / 7,200 (first election T + 4 h to T + 5.5 h, a new set and a key block every 4 h). The canonical 131,072 s / 65,536 s schedule left the first epoch without GC for 34 h |
| Validator retention | `network/profile.json` `retention`, `systemd/tos-testnet-validator.service` | `state_ttl` 3,600 s, `archive_ttl` 86,400 s; a test keeps the unit and the profile equal |
| D05 privacy | the template deploys no pool | disabled; version 16 (no `quantum-network-tag`) |
| D02 distribution | how operators receive `global-config.json` | the coordinator publishes it with its SHA-256; nodes install it only on a matching digest |
| Node binaries | `build-node-binaries.sh --rev <commit>`, then `install-node.sh prepare|binaries --release DIR` | every host compiles its own binaries from the pinned tos commit, for `x86-64-v2` (as tos CI does). Binaries are never copied from another machine: a build made on a Sapphire Rapids Xeon stopped with SIGILL on these Icelake VMs, because RocksDB defaults to `-march=native` |
| D11 faucet funding | nothing in genesis; the faucet wallet is ordinary | decided 2026-10-12: validator-donated rewards, canonical genesis. The first rewards unfreeze about T + 63.7 h, so the faucet opens on day 3 at the earliest |
| D13 release evidence | capacity and timing reports | decided 2026-10-12: not release evidence; labelled `NON-RELEASE` |

The template's other mainnet constants are kept on purpose: ConfigParams
8/12/14/15/16/17/30/47, supply and the bootstrap wallet. A testnet that changes
one of them is a different genesis and needs its own review.

## Genesis template patch

The canonical `gen-zerostate.fif` pins mainnet: `1 setglobalid` and a
`SOURCE_DATE_EPOCH` check for 1789434000, whose 131,072-second initial set
expired on 2026-09-16. `testnet-coordinator.py genesis` copies the template
into the ceremony directory and replaces exactly those three lines, plus the
two that set the validator schedule (`config.election_params!` and
`orig_vset_valid_for`, from the profile); if any of them is missing or appears
twice, the template changed and the ceremony refuses. The patched copy, the original's SHA-256, the tos revision and the
`create-state` digest are recorded in `genesis.json`, and genesis is generated
twice in separate directories and must be byte-identical. tos itself is not
modified.

## Watching the network

Retired consensus sessions are deleted at every key block, so `consensus/`
grows between elections and shrinks after each one (epoch 3: about 10 MB a
minute idle, 31 MB a minute at ~6.4M gas per block, back to about 750 MB after
each election). One host, on the host:

```bash
python3 /opt/tos-testnet/scripts/check-host-disk.py --min-free-gib 15 --cpu-sample 3
```

It prints free space, `consensus/` size and session count, the validator
unit's state, restarts and memory, the head seqno and age, the block-download
net failures and refused answers, and CPU busy and iowait; it exits 1 below
the floor. A value it could not observe is null, not 0.

All validators, from the coordinator (the hosts need nothing installed; the
probe is piped over SSH):

```bash
testnet/scripts/watch-testnet.py --inventory hosts.json --out epoch/series.tsv \
    --interval 60 --duration 1800
```

It appends one TSV row per host per round and prints `ANOMALY` / `RECOVERED`
lines when the set of anomalies changes (unreachable, unit not active, restart
count changed, head older than 120 s, head unchanged for three rounds, a burst
of five or more net failures in one round, free space below 20 GiB) and a
`SUMMARY` of heights every 15 minutes. Typical uses:

- the epoch watch: `--interval 60`, re-armed for as long as the epoch runs;
- the `consensus/` and memory series: `--interval 900`;
- a load test: `--interval 60 --cpu-sample 3` for the load window;
- a restarted validator's catch-up (CON-06): start it right after the
  restart with `--hosts node-4 --interval 30 --until-current node-4
  --duration 2400`; it prints `CURRENT ... after N s` once the shard client
  age falls below 60 s, or `NOT CURRENT` and exits 1.

After each rotation, confirm the elected set with the same records file used
at genesis (TOS_ROOT names a tos checkout to decode with):

```bash
TOS_ROOT=$TOS_ROOT "$TOS_ROOT/.venv/bin/python" testnet/scripts/check-testnet.py \
    --genesis genesis.json --rpc URL --rpc URL --elected-set genesis-records.json
```

It requires as many members as records, all main validators, with exactly the
records' controllers (consensus keys may change at an election), and prints
the set's `utime_since`/`utime_until`.

## Alerts

`scripts/alert-relay.py` turns the watch into messages to a person over a
Telegram bot. Two roles, on two hosts, each watching the other's heartbeat:

- `coordinator` (on the coordinator, `systemd/tos-testnet-alert-coordinator.service`
  as a user unit) runs `watch-testnet.py` with no duration and restarts it if
  it exits. It sends a message when an anomaly key (`node-1:head_age`,
  `node-3:unit`: host and kind, without the value) first appears, with the
  full `ANOMALY` line; one reminder per key every 30 minutes while it
  persists; and a recovery message naming what cleared. `SUMMARY` lines are
  not sent (`--digest-hours N` sends one every N hours). Every minute it
  touches `/var/lib/tos-alert/heartbeat-coordinator` on the `--peer` host over
  SSH (as root, handing the file to the directory's owner) and reads the age
  of `heartbeat-peer` there.
- `peer` (on the DHT host, `systemd/tos-testnet-alert-peer.service`, user `tos-alert`)
  touches `heartbeat-peer` every minute and alerts when the coordinator's beat
  is older than 150 s, then reports its return. While that beat is dead it
  also reads the chat's replies (see below).

Either side alerts once when the other's beat is stale or unreadable for
`--dead-after` (150 s) and sends a recovery when it is fresh. 150 s is two
missed one-minute beats plus slack: a stopped side is reported within
dead-after + one check interval + the send (at most about 260 s), inside the
5-minute alert budget. Telegram connections try IPv4 before IPv6, 3 s per
address, so a host whose IPv6 route hangs still sends in about a second. The bot token
and chat id are files given by `--token-file` and `--chat-file`, mode 0600
(the relay refuses anything group- or world-readable): `/etc/tos-alert/` on
the DHT host, root-owned and passed to the peer as systemd credentials (the
relay accepts a credential's ACL group bits, nothing else), and
`~/.config/tos-alert/` on the coordinator. They never enter this repository.

A reply in the chat is an acknowledgement: the coordinator reads replies
every 30 s, records each in `acks.jsonl` with its time and the alert it
follows, and confirms it. While the coordinator's heartbeat is dead, the peer
reads them instead (its own offset file, its own `acks.jsonl`, each reply
recorded against the peer's last alert) and stops when the beat is fresh
again, so only one host reads at a time. getUpdates confirms what it returns
on Telegram's side, so a reply one host read is never seen by the other: the
acknowledgement receipts are split between the two hosts' `acks.jsonl`, and
reading both is the full record.

Planned work: silence each host whose alerts it would trigger before you
start, for example on the coordinator and, over SSH, on the DHT host:

```bash
testnet/scripts/alert-relay.py silence --state-dir ~/.local/state/tos-alert \
    --until +90 --reason "restart node-2 for the new build"
ssh root@DHT-HOST python3 /opt/tos-testnet/scripts/alert-relay.py silence \
    --until 2027-01-15T10:00 --reason "coordinator reboot"
```

Run as root, `silence` hands the file to the owner of the state directory, so
the peer (user `tos-alert`) can read it.

While silenced, alerts are recorded but not sent; when the silence expires or
`unsilence` removes it, one message lists what was suppressed and what is
still active.

Receipts: every alert, sent or silenced, is a line in `alerts.jsonl` in the
state directory (`~/.local/state/tos-alert` on the coordinator,
`/var/lib/tos-alert` on the DHT host) with its UTC time, kind, keys, text,
Telegram message id and send latency; replies are in `acks.jsonl`. A message
that cannot be sent is retried every cycle and recorded only once it goes
out, so its latency shows the delay.

Known gap: the peer has no chain access (the validators' JSON-RPC answers on
loopback only), so it watches only the coordinator's heartbeat. It can say the
coordinator's watch stopped, but while the coordinator is down nobody watches
the chain, and the chain is only ever seen through the coordinator's SSH
probes. An independent chain observer needs a public read-only endpoint, which
is not deployed.

## Verification

`scripts/rehearse-loopback.sh` runs every script above on one host with four
operators and two DHT nodes, then starts the four validators and requires
`check-testnet.py` to see one zero state, one full block id at height 20 or
more, the testnet global id and ConfigParam 34 equal to the four genesis
identities:

```bash
TOS_ROOT=$TOS_ROOT TOS_BUILD=$TOS_ROOT/build testnet/scripts/rehearse-loopback.sh /path/to/new/workdir
```

Unit tests need only pytest (the tos environment has it). With `TOS_ROOT`
set they also check the patch against the real template, and with `TOS_BIN`
naming release binaries they exercise the console set-up:

```bash
TOS_ROOT=$TOS_ROOT "$TOS_ROOT/.venv/bin/python" -m pytest -q testnet/tests
```

Each guard was broken once on purpose and the tests failed every time:
identity uniqueness, template line count, key id match, block agreement,
global id, staleness, the config lock, the confirmed-global-id gate, key
reuse across resets (validator identities and wallet keys), and the validator
schedule checks.

After a reset, every coordinator step that creates or onboards a wallet takes
`--previous-ceremony DIR` once per earlier epoch (`testnet-coordinator.py
genesis`, `testnet-elections.py onboard` and `load`), beside `manifest
--previous`; see CEREMONY.md section 9.

## What is still open

- The plan's two independent G0 rehearsal receipts. Epoch 1 was a real
  multi-host run, but by one coordinator acting for all four operators.
- Elections: `testnet-elections.py onboard` (CEREMONY.md section 8.1) codifies
  what epoch 1 ran by hand. Its parsers are pinned to real `tosctl` output, but
  the whole command has not yet run end to end; its first run is the next
  epoch, and it must finish before the first election opens at T + 4 h
  (`genesis.json` `first_election`). `refund` replaces the hand-run renewal of
  the operating authorization the same way and has not run end to end either.
- Authenticated global-config distribution (production gap G7) and a refresh
  schedule for `init_block` (`scripts/refresh-global-config-init-block.py` in
  tos, run with `--global-id 2`).
- Public RPC proxy, explorer and monitoring placement (plan D07).
- The faucet service: donating operators, wallet custody, grant size and rate
  limits sized from measured issuance (plan D11, section 5.5).
